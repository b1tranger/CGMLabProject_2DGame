### AI Thinking & Planning Summary
> **Issue 1: Downward Ladder Movement**
>
> Investigation of the ladder latch detection condition in [`src/main.cpp`](/src/main.cpp) (Section 1: Proactive Ladder Shaft Detection & Latching) revealed that the latch condition only checked for:
> - `currentDirection == DIR_UP` or `DIR_DOWN` (already latched state)
> - `GLFW_KEY_W` or `GLFW_KEY_UP` (upward input keys)
>
> It did **not** check for `GLFW_KEY_S` or `GLFW_KEY_DOWN`. This meant a player standing on the surface ground directly above an underground ladder shaft could not initiate downward climbing by pressing `S`/`Down` — the ladder wouldn't latch them.
>
> Additionally, the Jump Input section had a climb-up handler that detects nearby ladders when `W`/`Up` is pressed and sets `currentDirection = DIR_UP`. There was **no analogous handler** for pressing `S`/`Down` to initiate downward ladder entry.
>
> **Fix**: Two-part solution:
> 1. Added `GLFW_KEY_S` and `GLFW_KEY_DOWN` to the ladder latch condition in the physics update loop.
> 2. Added a dedicated "Downward Ladder Entry" input handler in `processInput()` that detects when the grounded player presses `S`/`Down` near the top of a ladder shaft ($|X_{\text{player}} - X_{\text{tunnel}}| \leq 1.25$ and $Y_{\text{player}}$ near $Y_{\text{maxY}}$), then sets `DIR_DOWN`, latches onto the ladder, and begins descending at `CLIMB_SPEED`.
>
> ---
>
> **Issue 2: Leftward Movement Analysis**
>
> Deep code analysis of [`src/World.cpp`](/src/World.cpp) `World::updateProcedural()` confirmed that the world IS procedurally generated in **both** directions:
> - **Rightward**: `if (playerX + 35 > rightGenEdge)` triggers a new 35-unit chunk to the right.
> - **Leftward**: `if (playerX - 35 < leftGenEdge)` triggers a new 35-unit chunk to the left.
>
> Both directions use the **identical** `generateChunk()` function, which procedurally spawns bedrock, surface ground, cavern floors, elevated platforms, ladder tunnel shafts, steep slopes, spikes, relics, and coins. There is zero difference in the code path for left vs. right generation.
>
> **Why it might appear non-endless leftward**:
> - The initial chunk (`-25` to `35`, `isInitial = true`) returns early after placing only bedrock/surface/cavern tiles. The leftward stretch from `-25` to `0` has basic terrain but no platforms, ladders, relics, or slopes.
> - When the player starts at $X = 0$ and the default direction is `DIR_RIGHT`, leftward generation fires immediately (since $0 - 35 = -35 < -25$), generating a fully featured chunk from $-60$ to $-25$.
> - However, many players never manually turn left (pressing `A`) and may perceive the world as right-only. In reality, every time the player moves close enough to the left edge, another procedural chunk is generated — the world is infinite in both directions.
>
> **Static vs. Random Resource Usage**:
> - A **static (pre-generated) level** occupies fixed memory proportional to the entire level length. If the level were 10,000 tiles long, all tiles, objects, and collision data would exist in memory at all times.
> - The current **procedural (random) generation** creates chunks only when needed (within 35 units of the player) and **garbage collects** objects beyond 85 units behind the player (`std::remove_if` on every entity vector).
> - **Result**: Procedural generation uses far less memory for infinite worlds — only ~170 units of world data exist in memory at any moment, regardless of how far the player has traveled. Static generation for an infinite world would be impossible (infinite memory), and for a finite world would use more memory than needed since distant tiles would still be stored.
